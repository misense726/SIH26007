# Spatial mapping

The Spatial page uses the Three.js point-cloud renderer adapted from
`claude/nervous-gould-32361c`, commit `d70c1fb`. The view has a fixed perspective,
coloured point returns, solid yellow dump trucks and outlined non-vehicle objects.
The truck includes its hopper, cab and all wheels, with opaque shaded materials.
The primary truck and surrounding trucks share one model scale in each scene.
There are no orbit, plan,
zoom, coverage or grid controls, sensor rays or concentric distance rings.

## Data sources

- **LIVE:** recent ToF returns at their calibrated positions. These are planar
  measurements displayed in a 3D viewport, not a volumetric LiDAR scan.
- **SIMULATED:** sample the backend reference road and berms into a point cloud.
  Fleet objects move with backend poses. Berm heights are illustrative and the
  view is labelled SIMULATED MAPPING. Measured ToF points remain a separate buffer.
- **Missing data:** both modes show SIMULATED PREVIEW when no usable returns or
  simulated map are available. The preview is a deterministic visual fixture
  generated by `backend/app/simulation/spatial_preview.py` and shipped at
  `frontend/public/spatial-preview.json`. Its scan highlight is animated;
  it does not invent a live vehicle position or modify WorldState, localization,
  sensor health, safe corridors, or emergency state.
- **REPLAY:** show the recorded returns. Do not substitute a preview or start
  a haul cycle when the recording contains no spatial data.

The camera currently supplies images and visibility metrics, not calibrated
stereo or multi-view depth. The fallback is explicitly simulated, not camera
triangulation. Connecting a camera alone does not make its pixels metric depth.

## Coordinates and rendering

Backend coordinates use metres with +X right and +Y forward. Convert world
points to the current vehicle frame once, then render `(x, height, -y)` in
Three.js. ToF `height_hint_m` is illustrative, so measured points use a small
0.04 m display lift above the ground. No additional visual IMU rotation is
applied to their XY positions. The measured-view ego marker fits the calibrated
sensor mounting footprint; the simulated context uses an illustrative truck.

Keep the newest observation per sensor in each 4 cm world cell before applying
the 240-return display budget. Keep actual sample positions rather than snapping
them to cell centres. Share the budget between sources so repeated fixed-sensor
readings do not evict the scanner sweep. Reject low-quality, stale, disconnected,
unhealthy and out-of-range observations using planar distance from each mount.
Maximum-range readings are not obstacles. Backend warnings and latched emergency
stops remain visible independently of the point count or preview.

Tracked boxes ease to backend positions over 120 ms. Measured points and safety
state are not interpolated. Rendering pauses while hidden or outside the
viewport, reduced-motion disables continuous animation, and unmount releases
observers, listeners and GPU resources. Preview point buffers are cached.

## Shared truck geometry

`truckMesh.ts` builds the detailed dumper surfaces used by the supervisor mine
and shared truck renderers. `Vehicle3DTruck.tsx` is the SVG projection of that
geometry. Its tires, hopper, steering and face sorting remain available to
existing scenes; the Spatial page now uses the WebGL mapping renderer.

## Verification

Run `npm test` and `npm run build` from `frontend`, and
`python -m pytest backend/tests/test_spatial_preview.py` from the repository root.
Regenerate the preview with `python -m backend.app.simulation.spatial_preview`.

The development-only `/dev/spatial-review.html` page supplies labelled LIVE,
SIMULATED and REPLAY fixtures with dense, maximum-range, stale and disconnected
observations. Check source transitions, narrow layouts and context disposal.
These fixtures do not prove physical sensor placement or camera triangulation.
